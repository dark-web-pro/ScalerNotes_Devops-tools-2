Writing a Jenkinsfile
from scratch

A Jenkinsfile is just a text file, checked into your repo, that describes your CI/CD pipeline. Scroll down and we'll build one, block by block.

    01 · THE OUTER SHELL
    
Every Jenkinsfile starts with pipeline { }

    
This is the "declarative pipeline" syntax — the easiest and most common way to write a Jenkinsfile. Everything else you write lives inside this single block: where it runs, what stages exist, what happens in each stage, and what happens afterward.

    
The file itself is usually just named Jenkinsfile (no extension), committed at the root of your repo. Jenkins reads it whenever a Multibranch Pipeline or Pipeline job is triggered — that's what "pipeline as code" means: your build logic lives in version control next to the app, not clicked together in a UI.

    
i Declarative syntax is structured and predictable — great for teaching and for most real-world CI/CD jobs.

    
i There's also "scripted" syntax (raw Groovy, starts with node { }) — more powerful, more error-prone, and rarely where beginners should start.

    
i Declarative pipelines require exactly one top-level agent and one top-level stages block — that's the whole required skeleton.

  

  

    
pipeline {
    // everything goes here
}

  







  

    02 · WHERE IT RUNS
    
Tell Jenkins where to run the pipeline with agent

    
agent any tells Jenkins to run on whatever executor is free. In real setups you'll often target a specific label, like a Docker agent or a build node with the right tools installed.

    
You can also set agent none at the top level and instead give each individual stage its own agent block — useful when different stages need different environments (say, a Node container for the frontend build and a Python container for backend tests).

    
i agent { label 'linux' } pins the job to nodes tagged "linux".

    
i agent { docker 'node:20' } runs every stage inside that container — no need to install Node on the Jenkins host itself.

    
i agent none at the top + per-stage agents gives fine-grained control over where each piece of work happens.

  

  

    
pipeline {
    agent any
}

  







  

    03 · THE WORK ITSELF
    
stages holds one or more named stage blocks

    
Each stage is a labelled phase of your pipeline — Build, Test, Deploy, whatever your process needs. Blue Ocean and the classic UI both render these as the boxes you see in a running job, so a good stage name doubles as documentation for anyone watching the build.

    
A stage can also carry its own conditions: when { branch 'main' } skips a stage unless you're on a specific branch, and options { retry(2) } or timeout(time: 5, unit: 'MINUTES') can be scoped to a single stage instead of the whole pipeline.

    
i Stage names show up directly in the Jenkins UI, so name them for humans: "Build", "Unit Tests", "Deploy to Staging".

    
i Stages run top to bottom, in order, unless you explicitly parallelize them (more on that below).

    
i If any stage fails, later stages are skipped by default and the pipeline drops straight to post.

  

  

    
    stages {
        stage('Build') { ... }
        stage('Test')  { ... }
        stage('Deploy'){ ... }
    }

  







  

    04 · THE ACTUAL COMMANDS
    
Inside each stage, steps runs the real commands

    
This is where the shell commands, script calls, and build tool invocations actually live. sh runs a shell command on Linux/macOS agents; use bat or powershell on Windows agents. A steps block can contain as many individual steps as you need, executed in order.

    
Steps aren't limited to shell calls — plugin-provided steps like checkout scm (pull the repo), junit (publish test results), and archiveArtifacts (save build output) hook straight into Jenkins' UI, so results show up as trend graphs and downloadable files instead of raw console text.

    
i Keep steps simple and readable — call out to a shell script for anything longer than a few lines.

    
i Common steps: sh, echo, archiveArtifacts, junit, checkout scm.

    
i Environment variables go in a top-level or per-stage environment { } block, and are read inside steps as $VAR_NAME.

  

  

    
        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }

  







  

    05 · RUNNING STAGES AT ONCE
    
parallel runs stages side by side

    
Normally stages run one after another. When several stages don't depend on each other — say, running unit tests and a linter at the same time — wrap them in a parallel block inside a stage. Jenkins fans them out to separate executors and waits for all of them before moving on.

    
This is a real time-saver in training demos and in production: a five-minute test suite and a two-minute lint check run concurrently instead of stacking to seven minutes.

    
i Each branch inside parallel is itself a named block with its own steps — think of it as mini-stages inside a stage.

    
i By default, if one parallel branch fails, Jenkins still lets the others finish. Add failFast true to abort all branches the moment one fails.

    
i Parallel branches can each request their own agent, so "Unit Tests" and "Lint" can literally run on two different machines at once.

  

  

    
        stage('Test') {
            parallel {
                stage('Unit Tests') {
                    steps { sh 'mvn test' }
                }
                stage('Lint') {
                    steps { sh 'npm run lint' }
                }
            }
        }

  







  

    06 · AFTER THE PIPELINE RUNS
    
post reacts to the outcome

    
Sitting at the end of your pipeline block, post defines what happens after everything finishes — regardless of whether it passed or failed.

    
i always runs every time — good for cleanup and notifications.

    
i success and failure run only on that specific outcome — perfect for Slack alerts.

  

  

    
    post {
        success { echo 'Build succeeded ✅' }
        failure { echo 'Build failed ❌' }
    }

  







  PUT IT ALL TOGETHER
  
The complete Jenkinsfile


  

    

      

      

      

      Jenkinsfile
    

    
pipeline {
    agent any

    stages {
        stage('Build') {
            steps { sh 'mvn clean package' }
        }
        stage('Test') {
            steps { sh 'mvn test' }
        }
        stage('Deploy') {
            steps { sh './deploy.sh staging' }
        }
    }

    post {
        success { echo 'Build succeeded ✅' }
        failure { echo 'Build failed ❌' }
    }
}
